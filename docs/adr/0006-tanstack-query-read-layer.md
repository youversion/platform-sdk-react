# 6. TanStack Query backs the read layer

Date: 2026-08-24

Amended: 2026-09-01

## Status

Accepted

## Context

`useApiData` was a hand-rolled effect: every mount and every dep change refetched, nothing was cached, and disabling a query threw its data away. Revisiting a chapter re-blanked the reader; account data was cleared imperatively on auth changes, which is easy to get wrong once and leak one user's highlights to another. The hook-level call shape is documented in `packages/hooks/AGENTS.md`.

## Decision

Rewrite `useApiData` on TanStack Query v5, exact-pinned (`5.101.4`, no caret) as a direct dependency of `@youversion/platform-react-hooks`. The `QueryClient` is private: created inside `YouVersionProvider` (one per provider instance, `retry: false`), never accepted as a prop, never exported. `useApiData` takes an explicit query key; key bases come from provider config via `useQueryKeyBase` — app key, API host, installation id, the serialized `additionalHeaders`, and the serialized Bible version filter from `YouVersionPlatformConfiguration` (the filter decides which versions a read may return, so a provider that tightens it reads a different key and never serves content cached under the looser filter) — and account-scoped hooks (`useHighlights`) add a user segment from `useUserScope`: the `userId` when a user is identified, `'anon'` when nobody is or can be signed in, and `null` when the account is not known yet (auth still loading, or a signed-in profile with no `userId` — the field is optional). A `null` scope disables the query, so an unidentified account never reads or writes a cache entry. The public hook contract — `{ data, loading, error, refetch }` — is unchanged; nothing TanStack-shaped is exported.

Opted-in Bible queries — `GET /v1/bibles/{id}` and the subpaths used by the version, book, books, chapter, chapters, verse, verses, and passage hooks — take that query's `staleTime` and `gcTime` from remaining Cache-Control lifetime (`max-age` minus `Age`). The first fetch of a key still uses `staleTime: 0`; remaining lifetime is written after a successful opted-in response. Hooks that do not opt in (highlights, the versions list, VOTD, languages, organizations, theme, auth) keep the client default `gcTime` of five minutes and `staleTime: 0`. The query cache stays memory-only. Each `YouVersionProvider` owns a private `QueryClient`; Expo DOM WebViews do not share Bible memory. This is not YPE-5262. `retry`, `networkMode`, `refetchOnWindowFocus`, and `refetchOnReconnect` do not change.

## Why

- **Direct dep, not peer.** A peer would push an infrastructure choice onto every consumer and invite version skew against our compat mapping. Exact pin: the mapping (`isPending`, masking, invalidation) is version-sensitive, and the repo's 3-day `minimumReleaseAge` makes floating ranges a supply-chain surface.
- **Private client.** Exposing the client (or accepting the host's) makes our query keys public API and lets a host's defaults (retries, persisters) rewrite our semantics. Cost accepted: an app already using TanStack Query carries a second client and cache copy — bounded, memory-only. The provider also does not render TanStack's `QueryClientProvider`: when the host's own `@tanstack/react-query` import resolves to the copy this package pins, that provider would shadow the host's client for every host component rendered inside the SDK tree. The client travels on a package-private context instead and reaches `useQuery`/`useQueries` as an explicit argument, so TanStack's context is never touched in either direction.
- **User-scoped keys, not imperative clearing.** With the user id in the key, serving one account's rows to another is structurally impossible and switch-back restores the previous account's cache instantly. Clearing on auth transitions had to be remembered at every transition; keys cannot be forgotten. The guarantee needs the `null` scope to hold: `'anon'` as a fallback for *unidentified* accounts would put two of them in one entry, which is the leak the keys exist to prevent. Not fetching is the safe answer — `useHighlights` is public and defaults to `enabled: true`, so it cannot rely on callers gating on a resolved profile.
- **`retry: false`.** The pre-TQ layer never retried; TQ's default (3 retries with backoff) would delay error surfacing behind partner-visible repeat traffic.
- **`networkMode: 'always'`.** Hooks promise to attempt the request and report a transport failure as `error`. TQ's default pauses a fetch whenever the browser reports offline, which strands a first load at `loading: true` forever and, after a key change, leaves the previous key's data on screen with `loading: false` and no error — the reader would render the last chapter as though it were the requested one. The browser's offline signal is a hint, not a verdict; the request itself is the authority.
- **`refetchOnWindowFocus: false`.** TQ revalidates every mounted query when the tab regains focus; the pre-TQ layer did not, and a mounted reader holds several queries at once (version, books, chapter, highlights). For Bible content — which does not change while the reader is open — that is net-new partner-visible traffic buying nothing. For hooks that do not opt in, mount, key change, and `refetch` still revalidate, which is every point where staleness is actually reachable. That default is still `staleTime: 0`, not a blanket `staleTime` on the client — a global stale window would also suppress remount revalidation for highlights, the versions list, and VOTD. Opted-in Bible queries write a per-query `staleTime` from remaining Cache-Control lifetime after a successful response; a remount within that window serves from memory. A mounted observer may outlive expiry because focus refetch is off and reconnect is error-only.
- **`refetchOnReconnect` refetches errored reads only.** The option is the predicate `query.state.status === 'error'`. `networkMode: 'always'` makes TQ infer `refetchOnReconnect: false`, and with `retry: false` and focus refetch off, an errored read would then have no way back short of a remount or a page reload — reconnect is its recovery path. A settled read keeps its data and does not refetch, so a reconnect does not revalidate every mounted query at once (the same partner-traffic argument as focus).

## Consequences

Revisits of hooks that do not opt in render from cache with background revalidation (`staleTime: 0`). Opted-in Bible revisits within remaining lifetime serve from memory without a refetch; remount after expiry is a miss and fetches. A still-mounted observer may keep showing the body after expiry. Disabled queries mask (`data: null`) rather than drop their cache entry. Offline is not a distinct state: a request is always attempted and a failure surfaces through `error` (`networkMode: 'always'`). Across a key change, hooks keep returning the previous key's data with `loading: true` until the new data lands (`placeholderData: keepPreviousData`); the Bible reader's chapter-navigation treatment — current chapter dimmed under a spinner — depends on this. Account-scoped hooks (`useHighlights`) opt out via `keepPreviousData: false`, because their key carries the user scope and held-over data would cross accounts. `loading` covers three windows: the first load of a key (`isPending`), the placeholder window after a key change (`isPlaceholderData && isFetching`), and an errored read's retry while it is in flight (`isError && isFetching` — a reconnect or `refetch` recovery); without the third clause, a recovering hook would report `loading: false` with the stale `error` still set, and consumers would render the error state during the retry. A background revalidation of settled, non-errored data leaves `loading` `false`. Accepted behavioral deltas: (1) `refetch` of settled, non-errored data no longer flips `loading` — data updates in place (an errored read's retry does report `loading: true`, per the third clause); (2) a failed background revalidate surfaces `error` while cached `data` stays non-null; (3) returning to the tab no longer revalidates (`refetchOnWindowFocus: false`), so a change made elsewhere lands on the next mount, key change, or `refetch` for default-freshness hooks, and on remount after expiry, key change, or `refetch` for opted-in Bible reads — not on focus; (4) default `gcTime` (5 min) bounds how long "instant revisit" holds for hooks that do not opt in; opted-in Bible queries use remaining Cache-Control lifetime for both `staleTime` and `gcTime`. `useQueryKeyBase` derives the `additionalHeaders` key segment itself rather than reading `context.additionalHeadersKey`, which only `YouVersionProvider` computes: `YouVersionContext` is public, and a host that renders it directly sends its own headers on the request, so trusting the precomputed field would collapse two header sets onto one cache entry. An account with no `userId` has no cache key, so `useHighlights` does not fetch for it; the Bible reader's write gate matches that condition, because permitting writes an account can never read back loses them silently. Test seams that render `YouVersionContext.Provider` raw must also mount the package-private query-client context (`TestQueryClientProvider`, published under `@youversion/platform-react-hooks/test-utils`). The referential-stability workaround in `use-bible-reader-highlights.ts` (holding the previous parsed `serverColors` reference across byte-identical refetches) became redundant — structural sharing keeps the `highlights` reference stable — and was removed in the same change.
